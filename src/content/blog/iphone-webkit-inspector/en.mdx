I hand a lot of frontend work to Claude Code these days. After editing a page, it opens it in Playwright to check for console errors and misplaced buttons on its own. On a desktop browser, that works well.

It falls apart on the iPhone. Some bugs only show up in Safari on an iPhone: 100vh coming out wrong because of the address bar, the page jumping when the keyboard opens, or audio refusing to autoplay. Those have to be checked on a real phone, and Playwright can't attach to one, even though it attaches to Android without trouble.

So I wrote a Claude Code plugin that lets Claude drive Safari on an iPhone connected over USB or Wi-Fi, more or less the way you'd use DevTools. It's called iPhone WebKit Inspector, and the code is on [GitHub](https://github.com/GUMBOKIM/iphone-webkit-inspector).

```
/plugin marketplace add GUMBOKIM/iphone-webkit-inspector
/plugin install iphone-webkit-inspector@gumbokim
```

## Why Android works and the iPhone doesn't

### Android: the phone already speaks CDP

Playwright drives Chrome over CDP, the Chrome DevTools Protocol, which is also what the DevTools window uses to talk to the browser.

Chrome and app WebViews on Android speak CDP as well. With USB debugging on and the connection approved, the phone exposes a debug socket such as `chrome_devtools_remote` (an app's WebView needs the app to allow debugging), and `adb forward` connects it to a port on the Mac:

```bash
adb forward tcp:9333 localabstract:chrome_devtools_remote
```

After that, Playwright's `connectOverCDP('http://127.0.0.1:9333')` attaches, and code written for desktop Chrome runs against the phone unchanged. Both ends already speak the same protocol, so the only job is opening a path between them.

### iPhone: a different protocol

Safari on the iPhone supports remote debugging too. It's what you're using when you open an iPhone tab from the Develop menu in Safari on the Mac. That connection speaks the WebKit Web Inspector protocol, though, and its commands and message structure differ from CDP.

Playwright has no way in from its side either. `connectOverCDP` only works with Chromium-based browsers, and Playwright's WebKit support launches its own WebKit build patched for automation, so it can't attach to a Safari that's already running on an iPhone. You can't install a Playwright browser on the phone either. The iPhone Chrome I use runs on the same WebKit as Safari, so the Android trick of "it's Chrome, so it speaks CDP" doesn't carry over. It does expose the same Web Inspector as Safari, though, so the plugin works with iPhone Chrome too.

| | Android Chrome | iPhone Safari |
|---|---|---|
| Debugging protocol the browser speaks | CDP | WebKit Web Inspector |
| Path to the Mac | `adb forward` | USB (usbmuxd) or Wi-Fi |
| Attaching with Playwright | `connectOverCDP` just works | Not possible |

### Even with a bridge, Playwright wouldn't attach

Another route goes through the Python tool [pymobiledevice3](https://github.com/doronz88/pymobiledevice3). Its `webinspector cdp` command runs a CDP server on the Mac, translates incoming CDP commands into WebKit Web Inspector commands, and sends them to the iPhone. I'll call it the bridge from here on.

My first try was pointing Playwright at the bridge. `connectOverCDP` connected, but the page list came back empty, and I didn't dig into why. Google's chrome-devtools-mcp got further, but some of the Accessibility and Emulation commands it needed weren't supported, so I couldn't use all of it.

I gave up on attaching Playwright and built the features I needed on top of the bridge instead. It translates the basic CDP commands I need, and a command it doesn't translate still goes through if you send it under its WebKit name. Between the two, most of what I'd do in DevTools was covered.

### Running the bridge with uvx

pymobiledevice3 runs through `uvx`, which runs a Python tool in an isolated environment without installing anything globally. I pinned it to the version I tested.

It works over USB and Wi-Fi. With a cable plugged in, it goes through macOS's usbmuxd. Without one, it borrows the wireless connection that macOS already keeps open to the iPhone for Xcode (the CoreDevice tunnel), and in my setup a phone that had been paired once and was on the same network connected without any changes in Finder.

### A daemon holds the connections

The first version opened a new connection to the tab for every command. Attaching to an iPhone tab took 5 to 20 seconds the first time, and reconnecting sometimes hung, which ruled it out for an AI that runs dozens of commands in a row.

Now a background daemon keeps one connection open per tab. The first command starts it, and after that a simple command like evaluating one line of JS takes about 10ms. The daemon keeps recording console messages and network requests for the tab it's working on, so asking for "the error from earlier" works too.

### Snapshots and refs for the AI

Give an AI a screenshot and ask it to tap the login button, and it has to guess coordinates from the image, which is slow and often misses. Playwright MCP gets around this by numbering the elements on screen, and I borrowed that idea.

`snapshot` lists the links, buttons, inputs and headings currently on screen, each with a number like `@e1` or `@e2`. Here's one of my blog posts open on the iPhone:

```
$ node ios.mjs snapshot
브라우저로 플립닷 디스플레이 만들기: 딸깍 소리까지 | gumbo — https://blog.daeheekim.dev/posts/flip-dot/
viewport 393×659, scrollY 750 (visible part only; --all for the whole page)
@e1   link         "invidis"  192,69,38,17
@e2   heading      "바로 눌러 보기"  20,126,354,33
@e3   button       "시계" [pressed]  20,186,47,31
```

The AI then acts by number with `tap @e3` or `type @e5 hello`. If another element covers the target, `tap` doesn't press anything and reports what's in the way.

A tap doesn't touch the screen; it sends touch and click events from inside the page. Events created that way normally aren't allowed to do things that need a real user action, like starting audio or going fullscreen. WebKit has an option that runs code as if the user triggered it (`emulateUserGesture`), and taps and typing run with it turned on, so the AI can check that a button's audio playback isn't blocked.

### The DevTools features

Once connecting and input worked, I added the DevTools features I normally use, one command at a time.

| What you'd do in DevTools | Command |
|---|---|
| Which file and line an element's CSS comes from | `styles` |
| Accessibility info, event listeners, compositing layers | `a11y`, `listeners`, `layers` |
| Console, failed requests, request and response bodies, HAR | `logs`, `net`, `req`, `body`, `har` |
| Block requests, mock responses, disable cache | `block`, `mock`, `nocache` |
| Breakpoints, pause on exceptions, step through | `break`, `pause-on`, `step` |
| Cookies, localStorage, IndexedDB | `cookies`, `storage`, `idb` |
| Load timings, performance traces, CPU profiles, heap snapshots | `perf`, `trace`, `profile`, `heap` |
| Dark mode, paint flashing, User-Agent override | `media`, `paintflash`, `ua` |

Ask it to check a post's load time on the iPhone, and the AI starts with `perf`:

```
$ node ios.mjs perf
page   h2  dns 52ms  connect 238ms  ttfb 242ms  html 3ms  (12.4k → 46.5k)
events domInteractive 575ms  DOMContentLoaded 957ms  load 985ms
paint  FCP 986ms  LCP -  CLS -
```

Traces from `trace` are saved in Chrome's format and open as they are in the Performance panel of Chrome DevTools.

### Working around what the bridge drops

This took the most time. Often I'd send a CDP command and the bridge would ignore it quietly or return something odd, and each time I went through its source looking for another route.

`Runtime.evaluate` ignores its `awaitPromise` option, so code that has to wait on a Promise stores its result in a global on the page, and the daemon polls until it's there. `Page.addScriptToEvaluateOnNewDocument`, which runs a script before the page's own, gets dropped, so I use WebKit's `Page.setBootstrapScript` instead. Listing event listeners failed with the CDP command I tried, so I call WebKit's `DOM.getEventListenersForNode`, which also reports listeners on parent elements and turned out to be more useful anyway.

Two more problems couldn't be fixed by swapping commands, so I worked around them in the output and in how the tool is used. The gaps between CPU profile samples are mostly zero with the occasional huge one, so the profile shows each function's share of samples instead of milliseconds. And a trace that spans a move to another site came back nearly empty. That seems related to Safari switching processes between sites, so the skill tells the AI to trace a reload on the same site.

### Capturing Safari's bars and the keyboard

A Web Inspector screenshot covers only the web page. iPhone bugs often involve the address bar or the keyboard, though, so I wanted Safari's bars and the keyboard in the picture.

I used the device services behind Xcode for that. pymobiledevice3 can talk to them too, so `shot --device` captures the whole iPhone screen at the device's own resolution (1179×2556 on my iPhone 15 Pro). The same services report the Core Animation FPS for the whole screen, so you can run an animation and watch for dropped frames in numbers. Launching Safari or opening a URL goes through Xcode's `devicectl`.

### Unix sockets instead of local ports

At first, both the daemon and the bridge listened on local TCP ports on `127.0.0.1`. I assumed that was fine since only my Mac could reach them. Once it was done, I had two other AI coding tools, Codex and Antigravity, review the code, and both flagged the same problem.

Listening only on localhost didn't keep web pages out. Depending on the browser and its settings, a page open on the Mac can open a WebSocket to `ws://127.0.0.1:...`, and that page could then run JS in my iPhone tab. Other user accounts on the same Mac could reach those ports as well.

Refusing requests with an `Origin` header blocked the web page case, but that did nothing about other users on the same Mac. Both now listen on Unix sockets in a folder only my account can open (mode 700). Other user accounts can't get at the sockets, web pages can't reach Unix sockets at all, and there are no tokens or secrets left to manage.

The bridge only knows how to listen on a TCP port, so at startup I intercept its web server settings and swap in the socket path. Node's built-in WebSocket only connects over TCP, so I wrote a small WebSocket client for Unix sockets, a bit over 100 lines.

### Packaging it as a Claude Code plugin

The plugin is a single skill. `SKILL.md` says when to use it ("check this on my iPhone", "look at it in mobile Safari"), the order to run the commands in, and what to undo afterward. `ios.mjs` is the Node script that does the work, with no npm dependencies, so there's nothing to install. I also installed the same repository as a Codex plugin, and it worked there as well.

An iPhone may have mail or banking open, so the skill tells the AI to work only on the tab the user pointed at or one it opened itself. In the code, console and network recording are turned on only for that tab, and if it closes, commands stop instead of quietly moving to another one. Page content the AI reads still goes into its session as tool output, so it's best used on tabs you're fine sharing.

## What doesn't work yet

Only the tab on screen renders. Background tabs still answer JS, console and network commands, but screenshots only capture the visible tab, and code can't bring another tab to the front.

Safari's own UI is out of reach: the address bar buttons, permission prompts, share sheets and the keyboard. On the device I tested, filling an input with `type` didn't bring the keyboard up, so keyboard checks still need someone to tap the input once. After the keyboard is up, `shot --device` can capture the screen with it.

On the iOS 18.6.2 device I tested, Safari didn't report LCP or CLS, so those two stay empty in `perf`. There's no network or CPU throttling either; for slow networks, turn on Network Link Conditioner in the iPhone's Developer settings.

## Wrapping up

You need macOS, Xcode, `uv` (`brew install uv`), Node 22 or later, and an iPhone on iOS 17 or later with Developer Mode and Safari's Web Inspector turned on. I tested on an iPhone 15 Pro with iOS 18.6.2. Install with the two commands above, then ask the AI to run `doctor` to check the setup step by step.

I used to open the Develop menu in Safari on the Mac and dig through iPhone-only bugs by hand. Now I ask the AI to check the page on my iPhone.
